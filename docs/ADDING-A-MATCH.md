# Adding a match

One command takes a match from its raw tracking files to chapter pages and all ten Analysis views. Two more
build the hub and the static site. This guide covers what a match needs, the registry entry, the run, and
the parts that stay manual.

## 1. Raw files

The pipeline reads **PFF FC's layout**, one folder per match (default `data/<match id>/`; set `DSM_DATA` to
keep data elsewhere):

| File | Used for |
|---|---|
| `tracking.jsonl.bz2` | player and ball positions per frame, with the embedded event feed (shots, ball out of play) |
| `roster.json` | shirt numbers, positions, starters, keepers |
| `metadata.json` | teams, pitch size, frame rate, which way each team starts |
| `events.json` | on-the-ball events, and PFF's analyst pressure tags (used to calibrate engaged vs passive) |

Other providers go through a converter in `providers/` that writes these four files (see
[providers/README.md](../providers/README.md) for the DFL Bundesliga converter).

## 2. Registry entry

Every per-match fact lives in `pipeline/matches.json`, in hub order. Copy an existing entry and set:

- `id`: the provider's game id. `slug`: short, like `bel-can`; it names every image and analysis file.
  `hub_id`: a unique id for the hub's chapter picker.
- `raw_dir`: `data/<id>`, or an absolute path.
- `title`, `sub`, `competition`, `label`: text for the hub, the images and the chapter pages.
- `home` / `away`: the provider's team `id`, `name`, a three-letter `code`, `color` and a darker `color_dim`.
  Pick colours that read on a dark green pitch and differ from each other.
- `goals`: `[[team name, minute, "" or "pen"], ...]`, from the match record. Used on timelines and to mark
  goals among the chances conceded.
- `provider`: `pff` (default) or `dfl`. It picks the data credit and the engaged/passive threshold source.
- `head_template`: `templates/artifact_head_<id>.html` (generated by the run).
- `chapter_urls`: `chapter_urls_<id>.json` (written after publishing). `site_folder`: the site folder name,
  like `belgium-canada`. `hub_note`: one paragraph for the hub (optional).
- `heatmap_vmax_log`: the danger heatmap's brightness ceiling (log scale). The 99.5th percentile of the
  match's danger values is a good default.
- `quirks`: `{}` unless validation reports something (step 3).

## 3. Run it

```
python3 pipeline/run_match.py <id> --only validate     # about a minute: read its output first
python3 pipeline/run_match.py <id>                     # everything else, about 35 minutes
python3 pipeline/run_match.py --list                   # the steps
```

**validate** checks the raw files and writes `output/derived/<id>.json`: the attack direction per period
(where each team's shots went decides; the metadata's start sides and the keepers' positions are
cross-checks), the frame rate, whether a per-player speed field exists, and warnings. If it reports a
**keeper swap** (the tracking labels the two keepers the wrong way round, as in the 2022 final's extra time),
copy it into `quirks.keeper_swap` so the fix is part of the registry.

The steps, in order:

| Steps | What they make |
|---|---|
| `validate` | directions, quirks, checks |
| `tracking_features`, `transitions`, `classification`, `pressure`, `merge_pressure`, `engagement` | the per-frame feature table: shape, phase, pressure, engaged/passive |
| `export`, `compactness`, `marking`, `export_marked`, `heatmap`, `head`, `build` | the chapter pages in `output/chapters_<id>/`; the tight/loose tag is computed from the first export, so the chapters are exported again to carry it |
| `events`, `positions` | the event feed and 5 Hz positions the Analysis views share |
| `attack`, `teams`, `players`, `shape`, `time`, `gaps`, `lb`, `turn`, `chances`, `press` | the ten Analysis views in `output/analysis/<view>/<slug>.{png,jpg,json}` |

Each successful step leaves a marker in `output/runs/<id>/`, so an interrupted run carries on where it
stopped; logs are in `output/logs/<id>/`. `--from <step>` re-runs a step and everything after it,
`--only <step> ...` runs just those, `--redo` ignores the markers. The runner sets `PYTHONHASHSEED=0`:
without it the player order inside the chapter data changes between runs (same content, different bytes).

## 4. Publish, report, build

1. **Chapters.** Publish `output/chapters_<id>/pressure_read_NN.html`, save the links as the registry's
   `chapter_urls` file (`{"chapters": {"1": url, ...}, "index": hub url}`), patch the prev/next links with
   `MATCH_ID=<id> python3 pipeline/full_match_patch.py <that file>` and republish. Then record them for the
   hub: `python3 pipeline/build_match_hub.py --chapters <id>`.
2. **Scouting reports.** Write one report per team in `content/reports.json`: a headline, three things it
   did well, three ways to get at it, and the Analysis views it draws on. Base every claim on the views'
   JSON in `output/analysis/`. The five stat chips and their ranks are computed, but ranking words written
   into the text ("the most compact of the twelve") are not: re-check them whenever a match is added.
3. **Hub and site.** `python3 pipeline/run_match.py hub` rebuilds the comparison board, the reports and the
   hub page (`output/hub/`). `python3 pipeline/build_site.py --extra <previous site export>` builds the
   self-hosted site in `output/site/`, with every claude.ai link rewritten to a relative path.

## 5. Things to know

- **Engaged/passive threshold.** Each PFF match calibrates its own against PFF's analyst pressure tags
  (`output/engagement_threshold_<id>.json`). A match without tags (DFL) uses the median of the calibrated
  matches, recorded as `"source": "pooled"`, so the PFF matches must be run first. Morocco vs Spain's
  pressing view uses a fixed 0.66 (`press_threshold_override`), from before per-match calibration.
- **Speed field.** Some PFF matches carry per-player speed and some don't (validate says which). Without it,
  pressure uses each player's top speed estimated from the smoothed positions.
- **Analysis tabs need every view.** The hub lines the views up by position, so a match shows in the Analysis
  section only once all ten are built; the builder says which matches it left out.
- **Credits.** Images and pages name the data source through `R.credit()` in `pipeline/registry.py`. PFF text
  passes through untouched; DFL matches get the CC-BY credit. A new provider needs its own `CREDITS` entry
  and an entry in `make_head.py`'s `PROVIDERS`.
- **Companion pages** (the Behind the Model charts and the broadcast-footage pages) are not rebuilt by this
  pipeline. The site builder copies them from a previous export.
